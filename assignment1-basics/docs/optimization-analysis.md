# BPE 训练流水线 — 性能优化分析

> **日期:** 2026-07-22
> **语料:** TinyStoriesV2-GPT4（训练集: 2.2 GB, 验证集: 22 MB）
> **分析目标:** `cs336_basics.tokenizer.train.train_bpe`

## 1. 各阶段耗时分布

在 `TinyStoriesV2-GPT4-valid.txt`（22 MB, vocab_size=1000）上实测：

| 阶段                | 耗时 (s) | 占比       |
| ------------------- | -------- | ---------- |
| `load_text`         | 0.05     | 1.3 %      |
| `pretokenize+count` | **2.74** | **78.6 %** |
| `build_structures`  | 0.05     | 1.5 %      |
| `training_loop`     | 0.65     | 18.6 %     |
| **总计**            | **3.49** | 100 %      |

**按完整训练集（2.2 GB，约 44× 倍）外推：**

| 阶段                | 预估耗时             |
| ------------------- | -------------------- |
| `load_text`         | ~2 s                 |
| `pretokenize+count` | **~120 s（2 分钟）** |
| `build_structures`  | ~2 s                 |
| `training_loop`     | 取决于 `vocab_size`  |

## 2. 瓶颈分析

### 2.1 预分词（占总耗时 78.6%）— **主要瓶颈**

GPT-2 正则表达式使用了 Unicode 属性类（`\p{L}`、`\p{N}`），这些语法需要第三方
`regex` 模块支持（Python 内置的 `re` 不支持）。对于 22 MB、约 530 万个预分词
token 的文本，仅正则匹配就耗时约 2.4 s，即吞吐量约为 **9 MB/s**。

**根本原因：** 正则引擎必须逐字符扫描全部文本，在每个位置评估所有分支选项。
Unicode 属性查找比简单的 ASCII 字符类开销大得多。

**难以修复的原因：**

- GPT-2 的正则模式**不能**修改，否则会改变分词行为，破坏与 GPT-2 生态的兼容性。
- **无法**用 `re` 替换 `regex`，因为 `re` 不支持 `\p{L}` / `\p{N}`。
- 并行化不简单：正则匹配可能跨越任意字节边界，分块处理文本需要仔细处理重叠区域。

### 2.2 训练循环（占总耗时 18.6%）

基于堆的增量合并循环已经足够高效（均摊 O(N log N)，N 为合并次数）。每次迭代从堆中
弹出最优 pair，应用于所有受影响的词，并推送更新后的 pair 计数。过期条目被惰性跳过。

**当前算法已接近该方法的理论下限，不存在明显的微优化空间。**

### 2.3 `load_text` 和 `build_structures`（可忽略不计）

内存映射 I/O（`mmap`）和 `build_structures` 数据结构的构建均为亚秒级操作。

## 3. 已实施的优化

| #   | 优化项                                                                                                                                 | 效果                                                                                   |
| --- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 1   | **`bytes` 键** — `token_sequences` 字典使用 `bytes` 而非 `tuple[int, ...]` 作为键                                                      | 消除了每个词的 `tuple()` 转换开销；每个键的内存占用减少约 4×                           |
| 2   | **流式 `finditer` + `Counter`** — 预分词结果直接计入 `Counter`，不生成中间列表                                                         | 避免存储约 500 万~5 亿个字符串对象的列表；内存峰值从 O(总 token 数) 降至 O(去重类型数) |
| 3   | **自适应 `findall` / `finditer`** — 文本小于 50 MB 时使用 `regex.findall`（快约 25%，基于列表）；超过阈值时回退到流式 `regex.finditer` | 中小文件提速约 25%，大文件保持内存安全                                                 |
| 4   | **预编译正则** — `_COMPILED_GPT2 = regex.compile(GPT2_PATTERN)`                                                                        | 效果有限——`regex` 内部已有缓存；主要是代码可读性的提升                                 |
| 5   | **快速子串检查** — 在决定是否按特殊 token 分割文本之前，用 `any(tok in text for tok in special_tokens)` 替代 `regex.search()`          | 避免特殊 token 不存在于语料中时（常见情况）不必要的全文正则扫描                        |
| 6   | **分阶段计时** — `train_bpe` 训练结束后打印耗时表格                                                                                    | 无需外部性能分析工具即可直接看到瓶颈所在                                               |

## 4. 后续优化方向

以下方案**尚未实施**——需要架构层面的改动或权衡，应根据项目需求评估。

### 4.1 分块 / 并行预分词（高收益，高工作量）

在安全边界（如换行符或特殊 token）上将文本分割为多个块，使用 `concurrent.futures` 并行处理。GPT-2 模式的匹配结果是行局部的（没有任何分支会跨行匹配），因此以换行符为边界进行分块是可行的。

- **预期加速比:** 多核机器上 4~8×
- **风险:** 分块边界的处理需要针对边界情况进行验证（尾部空白符、跨越块边界的缩写形式等）
- **复杂度:** 中–高

### 4.2 针对纯 ASCII 语料简化正则（中等收益，低工作量）

如果确认语料仅含 ASCII 字符（如 TinyStories），可将 `\p{L}` 替换为 `[A-Za-z]`，
将 `\p{N}` 替换为 `[0-9]`。对于简单字符类，Python 内置的 `re` 比 `regex` 更快。

- **预期加速比:** 预分词阶段 2~3×
- **风险:** 对非英文文本失效；需要语料检测或增加开关参数
- **复杂度:** 低

### 4.3 内存映射 + 即时解码（低收益，高工作量）

不使用 `mmap.read().decode('utf-8')`（会在内存中创建一个完整的 2.2 GB Python 字符串），
而是在 mmap 缓冲区上使用流式 UTF-8 解码器。

- **预期收益:** 内存峰值从约 2.5 GB 降至约 100 MB
- **速度影响:** 可忽略（解码器的工作量不变）
- **复杂度:** 高 —— Python 的 `codecs.iterdecode` 需要仔细管理缓冲区

### 4.4 Rust/C 扩展实现预分词（极高收益，极高工作量）

将正则匹配与计数逻辑移至编译型语言实现。

- **预期加速比:** 10~50×
- **复杂度:** 极高
- **不推荐** 在作业环境下使用 —— 保持纯 Python 实现的教育意义大于性能收益。

## 5. 建议

1. **开发环境 / 小语料（< 50 MB）：** 当前流水线速度足够，无需进一步优化。自适应
   `findall` 路径提供了最佳的单线程吞吐量。

2. **完整 TinyStories 训练集（2.2 GB）：** 训练到 `vocab_size=10000` 时，预分词
   预计约 2 分钟。对于一次性训练运行来说可以接受。

3. **生产级语料（10+ GB）：** 实施分块并行预分词（第 4.1 节），这是性价比最高的下一步。

4. **内存受限环境：** 实施流式 UTF-8 解码（第 4.3 节），避免分配与语料大小相当的
   Python 字符串。
